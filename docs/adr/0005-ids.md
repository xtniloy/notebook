# ADR 0005: Identifiers

- **Status:** Accepted
- **Date:** 2026-10-29
- **Task:** 2.1

## Context

Folders, notes and attachments exist on several devices once sync is on
(Plan §9), and are restored onto new devices from Google Drive. Each device has
its own SQLite database, where integer `INTEGER PRIMARY KEY` row ids are fast
for joins and indexes but are assigned independently: row 42 on one laptop is
a different note from row 42 on another.

Remote files are named by identity only, so no titles leak to Google
(`notes/<uuid>.bin`, Plan §9.4). Links between notes (`note://`), attachment
references in note bodies (`attachment://`) and drag & drop data also need an
identity that survives sync and restore.

## Options

- **A: Integer ids only,** with a remapping table per device. Fragile; every
  reference inside a note body would need rewriting on sync.
- **B: UUIDs only,** as primary keys. Globally unique, but 36-byte text keys in
  every join and index, and larger, slower tables.
- **C: Both:** a UUID as the stable identity everywhere outside one database,
  and an integer `id` for everything inside it.

## Decision

**Option C.**

- Every synced row has `uuid TEXT UNIQUE NOT NULL` (Plan §7): folders, notes,
  attachments, and later smart folders.
- UUIDs are **random version 4**, from `QUuid::createUuid()`, stored and sent as
  `toString(QUuid::WithoutBraces)`: 36 lowercase characters, e.g.
  `3f2504e0-4f89-41d3-9a0c-0305e82c3301`. Version 4 is random, so it reveals
  nothing about the device or creation time (unlike version 1).
- The integer `id` is **local only**. It is used for foreign keys, joins,
  in-memory references, and signals within the app (for example,
  `folderSelected(qint64)`). It never leaves the device: not in sync records,
  not in exports, not in links or clipboard/drag data.
- Anything that crosses a device or process boundary references by UUID: sync
  records (a note names its folder by folder UUID), `note://<uuid>` links,
  `attachment://<uuid>` resources, the `application/x-notesapp-note-uuids` drag
  MIME type, Drive file names.
- UUIDs from outside (sync, import, drag & drop) are parsed with `QUuid` and
  rejected if invalid or nil, before any database lookup.
- **The default "Notes" folder has a fixed, well-known UUID** (a constant in
  code, chosen once in task 2.5). Every device creates it on first run; a fixed
  UUID makes the copies from two devices the same folder after sync, instead of
  two "Notes" folders.
- Tags have no UUID: they are identified by name and travel inside each note's
  record.

## Consequences

- Fast local queries on integers; global identity costs one extra indexed text
  column per table.
- Sync and restore need a lookup from UUID to local `id` when applying remote
  records (the `UNIQUE` index makes it cheap), plus `sync_map` for Drive file
  ids (task 9.0).
- Positive integers are SQLite row ids, so negative ids are free for virtual
  entries in the UI: All Notes is `-1`, Recently Deleted `-2`
  (`models/SidebarRoles.h`).
- A UUID collision is not a practical concern (122 random bits).

## Verification

- `TC-STO-011`: the default "Notes" folder exists after first run (task 2.5
  also checks its UUID is the well-known constant).
- Sync tests (Phase 9) check that remote records and file names contain UUIDs
  and never local ids.
